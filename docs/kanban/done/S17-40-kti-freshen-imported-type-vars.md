# Add `freshenImportedTypeVars` to KTI `loadDepBindings`

## Sequence: S17-40
## Tier: 9
## Former ID: (none)

- Companion stories: S17-39, S17-24 through S17-38, S17-44

## Summary

When the self-hosted driver loads imported dependency KTIs (via `loadDepBindings` in
`stdlib/kestrel/tools/compiler/kti.ks`), the deserialized `TVar` nodes retain their
original integer IDs from the KTI file. The self-hosted typechecker's fresh type-variable
counter (`counter.nextVarId` in `types.ks`) starts at 0 and is always positive.

If two different imported modules both contain type vars with overlapping IDs (e.g. both
have `TVar(0)`, `TVar(1)` in their exported schemes), and those type vars escape the
scheme during type-checking (e.g., as residual unification vars in non-scheme bindings),
the unifier will incorrectly treat them as the same variable, causing unsound type
merging.

The TS bootstrap compiler avoids this via `freshenImportedTypeVars`
(`compiler/src/compile-file-jvm.ts` lines 47–99): after loading each KTI it remaps every
`TVar(id)` in the imported bindings to a fresh **negative** ID using a separate reference
counter `importedTypeVarIdRef = { value: -1 }` (line 586). Since fresh vars from the
typechecker are always positive and imported vars are always negative, the two ID spaces
never collide.

The self-hosted driver must implement the same strategy, either with negative IDs or by
bumping the fresh-var counter past the maximum imported ID.

## Current State

`stdlib/kestrel/tools/compiler/kti.ks`:
- `loadDepBindings` (line 503+) calls `deserializeExports` / `deserializeTypeAliases` and
  merges the resulting `Dict<String, InternalType>` into `importBindings` without any type
  var remapping.
- `deserializeTypeFromObj` (line 208) restores `TVar` nodes with the raw integer `id` from
  the KTI JSON: `Ty.TVar(Opt.getOrElse(Opt.andThen(objGet(ps, "id"), asInt), 0))`.

`stdlib/kestrel/dev/typecheck/types.ks`:
- `counter = { mut nextVarId = 0 }` — single global counter, always positive.
- `freshVar()` always returns `TVar(counter.nextVarId++)`.
- No mechanism for negative or imported-range IDs.

TS reference:
- `freshenImportedTypeVars` (`compiler/src/compile-file-jvm.ts` lines 47–99): walks any
  `InternalType`, remapping every `TVar(id)` using a shared `importedTypeVarIdRef` that
  decrements from -1.
- Called on every imported binding after KTI load (line ~586).

## Goals

1. Add a `freshenTypeVars` utility function to `kti.ks` (or `types.ks`) that:
   - Takes an `InternalType` and a mutable counter ref starting at -1 (decrementing).
   - Returns a new `InternalType` where every `TVar(id)` that appears free in the type is
     remapped to a new negative ID, tracking the mapping so that the same original `id`
     always maps to the same fresh negative ID within one import batch.
2. In `loadDepBindings` (or a helper), after calling `deserializeExports` for each dep,
   call `freshenTypeVars` on each binding's type before inserting it into `importBindings`.
3. In `stdlib/kestrel/dev/typecheck/types.ks`, confirm that `freshVar()` can never produce
   a negative ID (since `nextVarId` starts at 0 and increments). This property must be
   guaranteed so the negative-ID space stays reserved for imported vars.

## Risks / Notes

- The negative-ID scheme mirrors the TS compiler exactly; the simplest implementation is a
  direct port of `freshenImportedTypeVars`.
- `TScheme` vars in the `vars` list must also be remapped (they are bound variable IDs that
  appear inside the scheme body). The remapping must be consistent: the same original ID
  must map to the same negative ID within one import session so that scheme bodies remain
  internally consistent.
- An alternative strategy: after loading all deps, bump `counter.nextVarId` to
  `max(counter.nextVarId, maxImportedVarId + 1)`. This avoids negative IDs but requires a
  first pass to find the max imported ID. The negative-ID approach is simpler.
- `TNamespace` types carry no `TVar`; no action needed for them during freshening.

## Impact analysis

This story is confined to the self-hosted stdlib loader and the regression corpus.

- `stdlib/kestrel/tools/compiler/kti.ks`: add the freshening walk and apply it in
  `loadDepBindings` before imported bindings enter `importBindings`. This is the behavior
  change that prevents imported `TVar` IDs from colliding across modules.
- `stdlib/kestrel/dev/typecheck/types.ks`: no runtime behavior change is expected here; the
  existing `freshVar()` monotonic counter remains the source of positive IDs. The plan
  should preserve that contract rather than widening the typechecker API.
- `tests/unit/kti_serialize.test.ks`: extend the current KTI load regression to prove
  imported IDs are freshened into the negative range and that `freshVar()` still yields
  positive IDs.
- `compiler/test/integration/kti-incremental.test.ts`: add a multi-module compile regression
  that imports the same symbol from two modules and typechecks successfully. The conformance
  typecheck harness is single-file and does not resolve cross-file imports.
- `docs/specs/kti-format.md` and `docs/specs/06-typesystem.md`: document the reserved ID
  split between imported KTI vars and fresh typechecker vars.
- `scripts/`: no code changes are expected, but the story must still be verified through the
  existing `./scripts/kestrel test` and compiler test entrypoints.

Rollback risk is low: the helper is localized to dependency loading, and reverting it only
restores the old collision-prone behavior. The main implementation risk is keeping scheme
binders and their occurrences synchronized while leaving non-type-var payloads unchanged.
